Something more akin to a traditional Audio Manager where the sources are pooled in a static singleton implemented using MultiAudioSource would look like this:

```csharp
using System.Collections.Generic;

public class AudioPool : MonoBehaviour {
	static AudioPool _i;

	static readonly Dictionary<string, List<MultiAudioSource>> audioPool = new();
	
	void Start() {
		DontDestroyOnLoad(gameObject);
	}
	
	public static AudioPool i {
		get {
			if (_i == null) {
				AudioPool x = Resources.Load<AudioPool>("AudioPool");

				_i = Instantiate(x);
			}
			return _i;
		}
	}

	public static bool PlayFirstAvailable(string name) {
		MultiAudioSource firstAvailableSource = GetFirstAvailable(name);

		if (firstAvailableSource != null) {
			firstAvailableSource.Play();
			return true;
		}

		return false;
	}
	
	public static MultiAudioSource GetFirstAvailable(string name) {
		if (!audioPool.ContainsKey(name)) {
			audioPool[name] = new List<MultiAudioSource>();
		}

		foreach (var multiAudioSource in audioPool[name]) {
			if (!multiAudioSource.IsPlaying()) {
				return multiAudioSource;
			}
		}

		MultiAudioSource newSource = MultiAudioSource.FromResource(_i.gameObject, name);
		audioPool[name].Add(newSource);
		return newSource;
	}
}
```

This is almost as basic as an audio pool can get, but it's clear that something needs to be responsible for initialization. Whose responsibility is it to call FromResource and FromResources? In this example, the only type of MultiAudioSource that's supported is one that only has a single clip with no optional parameters. To support optional parameters, someone needs to be the one to specify. At a glance, the first solution would be to pass the optional parameters into `GetFirstAvailable` (and `PlayFirstAvailable`, since it calls `GetFirstAvailable`), but then literally every location in code that would want to play an audio clip would have to pass the parameters (which would go unused if pool already contained a MultiAudioSource with that name). It also duplicates data, which isn't great. Maybe one place calls `PlayFirstAvailable` for one clip, but another may be played from dozens of different locations. Changing parameters at one of those locations won't change the variables everywhere, which gets the data out of sync and makes it inconsistent.

Maybe it would be better to initialize them all at startup, and then re-use the passed optional parameters. Maybe MultiAudioSource can also have a `Clone` function that returns an identical MultiAudioSource attached to the same object. Maybe cloning isn't the greatest idea, so the parameters would have to get saved somewhere to get re-used by the audio pool when it doesn't have an available audio source.

Maybe this audio pool is going to be extremely advanced, having lifetimes for each object that eventually expire, removing the actual AudioSource component from the object to save on resources. There are many options here.

If creating a singleton audio pool isn't appealing and the part that seems useful is use of a dictionary to easily access the MultiAudioSources is the goal, then use can go from looking like this:

```csharp
public class Cat : Monobehaviour {
    MultiAudioSource eatAudio;
    MultiAudioSource meowAudio;
    // Script declares a large number of audio sources here
    MultiAudioSource sleepAudio;
    
    public void Start() {
        eatAudio = MultiAudioSource.FromResource(gameObject, "eat");
        eatAudio = MultiAudioSource.FromResource(gameObject, "meow");
        // Script initializes a large number of audio sources here 
        eatAudio = MultiAudioSource.FromResource(gameObject, "sleep");
    }
}
```

to a class with its own local dictionary

```csharp
public class Cat : Monobehaviour {
    readonly Dictionary<string, MultiAudioSource> audioPool = new();
    
    public void Start() {
        audioPool.Add("eat", MultiAudioSource.FromResource(gameObject, "eat"));
        audioPool.Add("meow", MultiAudioSource.FromResource(gameObject, "meow"));
        // Script initializes a large number of audio sources here 
        audioPool.Add("sleep", MultiAudioSource.FromResource(gameObject, "sleep"));
    }
}
```

used to quickly access a desired audio clip: `audioPool["eat"].Play()`. Maybe it's even worth it to write a local pool with functions that support the optional parameters.

```csharp
public class LocalAudioPool {
    readonly Dictionary<string, MultiAudioSource> audioPool = new();
    
    public void AddSourceWithSingleClip(GameObject gameObject, string path, bool loop = false, string audioMixer = "SFX", float volume = 1F, float pitch = 1F, float spatialBlend = 0, float minDistance = 0, float maxDistance = 0, float dopplerLevel = 1F) {
        if(!audioPool.ContainsKey(path)) {
            audioPool[path] = MultiAudioSource.FromResource(gameObject, path, loop, audioMixer, volume, pitch, spatialBlend, minDistance, maxDistance, dopplerLevel);
        }
    }
    
    public void AddSourceWithMultipleClips(GameObject gameObject, string pathPrefix, int count, string audioMixer = "SFX", float volume = 1F, float pitch = 1F, float spatialBlend = 0, float minDistance = 0, float maxDistance = 0, float dopplerLevel = 1F) {
        if(!audioPool.ContainsKey(path)) {
            audioPool[path] = MultiAudioSource.FromResources(gameObject, pathPrefix, count, loop, audioMixer, volume, pitch, spatialBlend, minDistance, maxDistance, dopplerLevel);
        }
    }
 
    public MultiAudioSource GetSource(string name) {
        if(!audioPool.ContainsKey(name)) {
            return null; 
        }
        
        return audioPool[name];
    }
    
    public void Play(string name) { GetSource(name)?.Play(); }
    public void PlayRandom(string name) { GetSource(name)?.PlayRandom(); }
    public void PlayOnlyIfDone(string name) { GetSource(name)?.PlayOnlyIfDone(); }
}
```

<Aside type="tip" icon="starlight">
    If you're wondering how `GetSource(name)?.Play()` works, take a look at the documentation for null conditional operators <a target="_blank" href="https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/operators/member-access-operators">here</a>.
</Aside>

I think that this is okay. If `FromResource` and/or `FromResources` are updated to support more (or fewer) parameters in the future, these functions will have to be edited as well, so `LocalAudioPool` would have to be a part of the library, which would be fine.  It would look cleaner if the library's user had to null check `GetSource`'s result every time, but then it's more boilerplate on their end. This makes it so that someone using the library that passees an audio clip name with a typo or tries to play an audio clip before the pool is initialized is protected from NullReferenceExceptions. Ideally, the person using a `LocalAudioPool` would initialize the pool before trying to play any of its sources, so let's make it clear by using the builder pattern.

```csharp
public class LocalAudioPool {
    readonly Dictionary<string, MultiAudioSource> audioPool = new();
    
    LocalAudioPool(Dictionary<string, MultiAudioSource> audioPool) { this.audioPool = audioPool; }
 
    public MultiAudioSource GetSource(string name) {
        if(!audioPool.ContainsKey(name)) {
            return null; 
        }
        
        return audioPool[name];
    }
    
    public void Play(string name) { GetSource(name)?.Play(); }
    public void PlayRandom(string name) { GetSource(name)?.PlayRandom(); }
    public void PlayOnlyIfDone(string name) { GetSource(name)?.PlayOnlyIfDone(); }
    
    class Builder() {
        readonly Dictionary<string, MultiAudioSource> audioPool = new();
   
        public Builder AddSourceWithSingleClip(GameObject gameObject, string path, bool loop = false, string audioMixer = "SFX", float volume = 1F, float pitch = 1F, float spatialBlend = 0, float minDistance = 0, float maxDistance = 0, float dopplerLevel = 1F) {
            if(!audioPool.ContainsKey(path)) {
                audioPool[path] = MultiAudioSource.FromResource(gameObject, path, loop, audioMixer, volume, pitch, spatialBlend, minDistance, maxDistance, dopplerLevel);
            }
            
            return this;
        }
        
        public Builder AddSourceWithMultipleClips(GameObject gameObject, string pathPrefix, int count, string audioMixer = "SFX", float volume = 1F, float pitch = 1F, float spatialBlend = 0, float minDistance = 0, float maxDistance = 0, float dopplerLevel = 1F) {
            if(!audioPool.ContainsKey(path)) {
                audioPool[path] = MultiAudioSource.FromResources(gameObject, pathPrefix, count, loop, audioMixer, volume, pitch, spatialBlend, minDistance, maxDistance, dopplerLevel);
            }
            
            return this;
        }
        
        public LocalAudioPool Build() { return new LocalAudioPool(audioPool); }
    }
}
```

Now this is looking very nice. The only constructor for `LocalAudioPool` is private, so nobody can call `new LocalAudioPool()`. To get a new instance of `LocalAudioPool`, the script that wants it must go through the builder by using `new LocalAudioPool.Builder()`.

```csharp
public class Cat : Monobehaviour {
    LocalAudioPool audioPool;
    
    public void Start() {
        LocalAudioPool.Builder audioPoolBuilder = new LocalAudioPool.Builder();
        
        audioPoolBuilder.AddSourceWithSingleClip("eat");
        audioPoolBuilder.AddSourceWithSingleClip("meow");
        // Script adds a lot of clips to the builder here 
        audioPoolBuilder.AddSourceWithSingleClip("sleep");
        
        audioPool = audioPoolBuilder.Build();
    }
}
```

Pretty good, and even if someone using this library doesn't look at the documentation, the fact that the `LocalAudioPool`'s only constructor is private can give them a hint as to what they need to do. Pooling anything is pretty involved and changes from situation to situation. I won't go too in depth about how to properly pool audio here, but this is a good start.
